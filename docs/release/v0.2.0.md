# grammar-lang v0.2.0 — A Parser Generator That Runs at Runtime

**The core, and the hard part of the roadmap.** v0.2.0 turns the scaffold
into a working parser generator: describe a language's tokens, rules, and
operator precedence in Rust, call `build`, and get a minimized DFA lexer and
an LALR(1) parser — no code generation step, no build script, no macro. The
parser turns text into a concrete syntax tree or drives your own semantic
actions. Precedence and conflict resolution follow GNU Bison's rules exactly,
verified against Bison itself; conflicts Bison would resolve by default are
reported instead. Error messages list exactly the tokens that could have come
next.

## What is grammar-lang?

The parser-generator core of the `-lang` language-construction family, and
the substrate of its language generator. Where `parser-lang` helps write a
parser by hand, grammar-lang generates one from a description that is plain
data — so a language's grammar can come from a schematic, a configuration
file, or a test, and a malformed grammar is an error value rather than a
compile failure. It is an LGEN-tier crate, depending only on `token-lang`
and `diag-lang`.

## What's new in 0.2.0

### `Grammar` — describe the language

A by-value builder. Tokens come in three forms: `literal` (exact text, named
by that text, so rules say `"+"` or `"while"`), `pattern` (a regular
expression), and `skip` (trivia the parser never sees). Rules are written one
production at a time with `rule`; the first rule is the start rule. Precedence
levels are declared with `left`, `right`, and `nonassoc`, and `prec` overrides
a production's precedence — the classic unary-minus pattern:

```rust
use grammar_lang::Grammar;

let parser = Grammar::new()
    .literal("-")
    .literal("*")
    .pattern("n", "[0-9]+")
    .skip("space", " +")
    .left(&["-"])
    .left(&["*"])
    .right(&["NEG"])
    .rule("e", &["e", "-", "e"])
    .rule("e", &["e", "*", "e"])
    .rule("e", &["-", "e"])
    .prec("NEG")
    .rule("e", &["n"])
    .build()?;

assert_eq!(
    parser.parse("-2 * 3").unwrap().to_string(),
    r#"(e (e "-" (e (n "2"))) "*" (e (n "3")))"#,
);
# Ok::<(), grammar_lang::GrammarError>(())
```

### The lexer generator

Every token's pattern — Rust `regex` syntax for everything a lexer can use —
is compiled by Thompson's construction into one NFA over UTF-8 bytes,
determinized over byte equivalence classes, minimized with Hopcroft's
algorithm, and laid out as a flat table. Each transition carries two flags,
"a token ends here" and "nothing can follow", so the scan does one load and
one test per byte and single-character tokens stop at once; adding the second
flag alone nearly doubled lexing throughput. Longest match wins; on a tie a
literal beats a pattern, then the earlier declaration — keywords and
identifiers coexist with no special handling. Tokens that match the empty
string or can never win a match are refused at build time.

### The parser generator — Bison's semantics, stricter defaults

The rules become an LR(0) automaton; DeRemer and Pennello's relations compute
its LALR(1) lookahead sets; dense ACTION and GOTO tables follow. Each state is
settled exactly as Bison settles it: a production's precedence is its last
token's unless `prec` names another, precedence is applied before
reduce/reduce conflicts are judged, and states that only a disabled shift
could reach are dropped, conflicts and all. Where Bison would then pick a
default, `build` refuses the grammar and names the conflict:

```rust
use grammar_lang::Grammar;

let err = Grammar::new()
    .literal("-")
    .pattern("n", "[0-9]+")
    .rule("e", &["e", "-", "e"])
    .rule("e", &["n"])
    .build()
    .unwrap_err();
assert_eq!(
    err.to_string(),
    "shift/reduce conflict on `-`: shift in `e → e • - e`, or reduce `e → e - e`",
);
```

Grammars in which a rule can derive itself alone are refused too
(`GrammarError::Cycle`): with a precedence hiding the conflict, a
table-driven parser would otherwise reduce around the cycle forever. Every
parse terminates.

### `Parser` — trees, actions, tokens

- `parse` builds a concrete syntax `Tree` of `Node`s — spans, text, children,
  preorder descendants, and S-expression `Display` — stored flat, so deep
  trees build, print, walk, and drop without recursion.
- `parse_with` runs your `Actions` in postorder instead, moving children out
  of the parser's stack and lending token text from the input, so an AST, a
  value, or nothing at all is built with no intermediate tree.
- `tokens` runs the lexer alone and carries on past characters no token
  matches — what a highlighter needs.

The parser is immutable, `Send`, `Sync`, and `Clone`.

### Exact error messages

An LALR(1) table merges lookaheads, so on its own it can list tokens that
cannot actually follow, and may reduce before it notices an error. On an
error the parser replays the input to the stack it had when the bad token
arrived and checks every token, so `ParseError::expected` and the message are
exact. The cost falls only on input that fails. `to_diagnostic` turns the
error into a `diag_lang::Diagnostic`:

```rust
use grammar_lang::Grammar;

let parser = Grammar::new()
    .literal("(")
    .literal(")")
    .literal("+")
    .pattern("n", "[0-9]+")
    .left(&["+"])
    .rule("e", &["e", "+", "e"])
    .rule("e", &["(", "e", ")"])
    .rule("e", &["n"])
    .build()?;

// `)` can follow `1` inside parentheses, but not here.
assert_eq!(
    parser.parse("1)").unwrap_err().to_string(),
    "expected `+` or end of input, found `)`",
);
# Ok::<(), grammar_lang::GrammarError>(())
```

### Examples

Five runnable programs: `calculator` (evaluation in actions, precedence,
right associativity, unary minus), `json` (a full RFC 8259 parser building a
typed value with borrowed strings), `ast` (a typed AST built straight into an
`ast-lang` arena and walked with an `ast-lang` visitor), `diagnostics`
(errors rendered by `diag-lang`), and `highlight` (a highlighter from the
token stream).

### Tests and verification

- **Against references.** Property tests hold the generator to a canonical
  LR(1) construction merged by core — the definition of LALR(1) — over random
  grammars; the parser to an Earley recognizer on every short input,
  including where the first error falls and exactly which tokens could follow
  it; and token patterns, Unicode included, to a direct interpreter. Deep
  one-off runs of 100,000 cases each found no disagreement.
- **Against Bison.** A differential harness generated 4,000 random grammars
  with random precedence levels and `%prec` overrides and ran each through
  both this crate and GNU Bison 3.8.2, compiling Bison's parser with `gcc`.
  Setting aside the 1,350 that are unproductive or cyclic, the verdicts agreed
  on all 2,650 — 1,290 conflicted in both — and on the 1,360 both accepted,
  every one of 174,940 inputs produced the same acceptance and the same exact
  sequence of reductions. The harness found two places where the first
  implementation was stricter than Bison — conflicts in unreachable states,
  and reduce/reduce conflicts judged before precedence — and both now match.
- **Robustness.** Arbitrary text never panics a parser; the token stream
  always tiles the input; 100,000-deep nesting parses, prints, and drops.

### Dependency wiring

`token-lang` 1 (tokens, `Span`, `TokenKind`) and `diag-lang` 1
(`ParseError::to_diagnostic`) are wired. `lexer-lang`, `parser-lang`, and
`ast-lang` are deliberately not: the generated lexer is a byte-level table
with no use for a character cursor, the LALR(1) driver has no use for a
hand-written parser's helpers, and grammar-lang owns no AST — languages build
their own through `Actions`, as the `ast` example does with `ast-lang`. The
decisions are recorded in `dev/ROADMAP.md`.

workspace, on Rust stable and on the 1.85 MSRV:

```bash

cargo clippy --all-targets -- -D warnings
cargo clippy --all-targets --all-features -- -D warnings
cargo clippy --all-targets --no-default-features -- -D warnings
cargo test
```
