# grammar-lang v1.0.1: linear lexing

**Patch.** v1.0.1 makes the generated lexer linear in the input on every
text, and stops `parse` from reserving memory in proportion to a huge input.
The public API is unchanged.

## Fixed

### Lexing could go quadratic

The lexer takes the longest match at each position, and a longest-match scan
can read far past the token it finally returns. Take a grammar with a block
comment pattern and a `/` literal. On an unclosed `/*`, the comment pattern
scans to the end of the input, finds no `*/`, and the lexer falls back to
`/`. The next `/` started the same scan again. A file made of unclosed
comment openers therefore lexed in quadratic time:

| Input (`"/* "` repeated) | 1.0.0 `tokens` | 1.0.1 `tokens` |
|---|---|---|
| 30 KB | 0.29 s | 1 ms |
| 60 KB | 1.2 s | 2 ms |
| 120 KB | 4.4 s | 4 ms |
| 240 KB | 20 s | 30 ms |
| 3 MB | about an hour (extrapolated) | 0.11 s |

`parse` behaved the same way. An editor or language server that parses on
every keystroke could be stalled by such a file.

The lexer now keeps a small memo for each pass over a text. After a scan
falls back to a shorter token, the DFA states it passed through after its
last match are remembered with their positions, because no token can be
found from any of them. A later scan that reaches one of those states at
the same position stops there, with the match it already has. Each state
and position pair is remembered at most once, so a whole pass makes a number
of transitions linear in the input. Ordinary input, where no scan runs past
the token it returns, never adds to the memo.

`Parser::parse`, `Parser::parse_with`, `Parser::tokens`, and the replay that
builds exact error messages all use it.

### `parse` reserved memory for the whole input up front

The tree builder reserved room for about one node per three input bytes
before reading the first token, roughly 8 bytes per input byte. A 100 MB
input committed about 800 MB even when it failed on its first byte. The
up-front reservation is now capped at about 24 MiB, and the tree grows as it
is built. Inputs under about 3 MB reserve exactly what they did before.

## Changed

- The memo check costs a little on ordinary input. In a tight loop over
  `tokens`, short-token input is about 5 to 10% slower and the 1 MiB JSON
  benchmark about 50% slower (2.2 ms to 3.3 ms). `parse` on the same JSON is
  about 10% slower.
- The README said the parser is fuzzed. It is not. Arbitrary text goes
  through it in property tests, which check that it never panics and that
  the tokens tile the input, and the README now says that.
- `docs/API.md` explains in the lexer section that longest match can still
  look ahead without bound. A grammar whose patterns back off this way does
  not meet incremental-lang's rule that where a token ends may depend on at
  most one character after it.

## Tests

- `tests/linear.rs` lexes and parses a megabyte of unclosed comment openers
  and a long run with no way to finish a pattern, each under a deadline.
- A unit test counts DFA transitions over whole passes and holds them to a
  small multiple of the input length.
- A property test checks every token stream, for random patterns and random
  text, against a brute-force longest match.

## Compatibility

No public item is added, removed, or changed. MSRV stays 1.85.
